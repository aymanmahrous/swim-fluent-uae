# تقرير الاختبارات الآلية والأداء والأمان

**المشروع:** Swim Fluent UAE  
**تاريخ الفحص:** 2026-09-20  
**النطاق:** المستودع الحالي، ملفات CI، مسارات الحجز، migrations وRPCs، وتدقيق التبعيات.  
**حدود التنفيذ:** لم تُنفذ أوامر SQL على Production، ولم تُرسل طلبات كتابة إلى الموقع، ولم تُجرَ اختبارات اختراق أو تغييرات أمنية قد تؤثر في المستخدمين.

## الخلاصة التنفيذية

الحالة الحالية **مستقرة وظيفيًا مع وجود مخاطر مؤجلة يجب معالجتها على مراحل**. أضيفت بوابة اختبارات عقدية آلية تمنع تكرار العطل السابق الذي نتج عن غياب دالة `normalize_uae_phone` من سلسلة migrations. هذه البوابة تتحقق من عقد مسار الحجز، وجود دالة تطبيع الهاتف وصلاحياتها، ربط الحجز بـ RPC الآمن، وتشغيل اختبارات الحماية الخاصة بعمليات Production فقط عند وجود تفويض يدوي صريح. نجحت المجموعة الجديدة مع اختبار RBAC الحالي بنتيجة **9 اختبارات ناجحة و0 فشل**.

أكبر ملاحظة أمنية مؤكدة هي وجود **4 ثغرات في lockfile: ثلاث عالية ومتوسطة واحدة**. لا أوصي بتشغيل `npm audit fix` تلقائيًا دون فرع مستقل واختبارات build وpreview، لأن التحديثات قد تغير شجرة البناء. كما أن الموقع يملك بعض رؤوس الحماية وضوابط الجلسات والحجز، لكن لا يظهر تطبيق صريح لـ CSP أو HSTS، ولا توجد حماية CSRF موحدة لمسارات الموظفين المعتمدة على Cookie في الملفات التي تمت مراجعتها.

في الأداء، توجد نقاط تحتاج قياسًا في قاعدة اختبار قبل إضافة فهارس أو تغيير RPCs. أبرزها العدادات المتكررة في لوحات الموظفين، واستعلام `DISTINCT ON` على `content_metrics`، وترتيب طوابير العمليات، والبحث عن وظائف الوسائط، وتنظيف سجلات محاولات الحجز داخل المسار الساخن لكل طلب.

## 1. ما تم تنفيذه الآن

أضيف الملف `tests/booking-contract.test.mjs`. وهو اختبار ساكن لا يتصل بقاعدة البيانات ولا يرسل طلبات خارجية. يتحقق من وجود validation للحجز، منع تسريب الأسرار، استخدام `supabaseSecretRpc`, عدم تخزين الاستجابات مؤقتًا، وجود idempotency وhoneypot وقياس زمن النموذج، وتحويل فشل الخدمة إلى `503`.

تم توسيع أمر `npm test` ليشغل اختبارات `tests/*.test.mjs` و`tests/*.test.ts`، مع إبقاء أمر `test:rbac` مستقلًا. كما أضيف أمر `test:booking-contract` للتشغيل المستهدف. وتم ربط `npm test` مباشرة ببوابة CI بدل الاكتفاء باختبار RBAC وحده.

نجحت الاختبارات محليًا كما يلي:

| المجموعة | النتيجة |
|---|---:|
| اختبارات عقد الحجز وmigrations وProduction gates | 4 ناجحة |
| اختبارات RBAC الحالية | 5 ناجحة |
| الإجمالي | 9 ناجحة، 0 فشل |

تعذر فحص YAML محليًا بأداة Ruby لأن Ruby غير مثبت في البيئة الحالية. يوجد فحص YAML نفسه داخل CI، ولم أغيّر صيغة YAML خارج الإضافات المحددة.

## 2. خطة الاختبارات الآلية الجديدة

### المستوى الأول: اختبارات العقود الساكنة

يعمل هذا المستوى مع كل Pull Request. يجب أن يفشل إذا اختفت دالة تطبيع الهاتف من migration الأساسي، أو أصبحت صلاحياتها متاحة للأدوار العامة، أو توقف مسار الحجز عن استخدام RPC الخادمي، أو أزيل `no-store`، أو تغيرت بوابة Production إلى تشغيل تلقائي.

### المستوى الثاني: اختبارات migration على قاعدة مؤقتة

يجب تشغيل `test-full-supabase-migration-chain.sh` و`test-fresh-supabase-history.sh` و`test-booking-phone-foundation-migrations.sh` في CI عند تغيير `supabase/migrations/**` أو ملفات الحجز. يجب أن تغطي الاختبارات أربع حالات: قاعدة جديدة، قاعدة قديمة، تطبيق متكرر، وتطبيق السلسلة بعد دمج migration جديدة. عند الفشل، تُرفع سجلات migration وملخص `information_schema` كـ artifacts.

### المستوى الثالث: اختبارات SQL سلوكية

ينبغي إنشاء قاعدة اختبار مؤقتة واختبار الصلاحيات الفعلية للأدوار `anon` و`authenticated` و`service_role`. يجب التحقق من أن RPC المباشر غير متاح للأدوار العامة، وأن مسار ingress الخادمي وحده يستطيع تنفيذ العملية، وأن RLS و`SECURITY DEFINER` و`search_path` تعمل معًا كما هو مقصود.

### المستوى الرابع: اختبارات API غير إنتاجية

ينبغي إضافة اختبار HTTP على preview أو قاعدة اختبار منفصلة يغطي JSON غير صالح، الحقول الناقصة، UUID غير صالح، التواريخ والأوقات غير الصالحة، تجاوز rate limit، أخطاء Supabase، والاستجابة `503`. يجب منع هذا الاختبار من استخدام أسرار Production.

### المستوى الخامس: اختبار idempotency والتزامن

يجب إرسال الطلب نفسه بمفتاح UUID واحد مرتين بالتوازي إلى بيئة اختبار. النتيجة المتوقعة هي سجل منطقي واحد مع استجابة duplicate أو retry آمنة. يجب اختبار UUID مختلف، إعادة المحاولة بعد timeout، والنقر المزدوج من واجهة المستخدم. هذا هو الاختبار الأهم لمنع إنشاء حجوزات مكررة.

### المستوى السادس: اختبار واجهة المستخدم

يُضاف Playwright على preview فقط للتحقق من مسار الحجز بالعربية والإنجليزية، القراءة من اليمين إلى اليسار، رسائل validation، منع الإرسال عند عدم قبول الشروط، ومنع النقر المزدوج. يبقى اختبار Production الكتابي يدويًا ومقيدًا ببوابة التفويض الحالية.

## 3. مراجعة أداء قاعدة البيانات

هذه النتائج مستخرجة من قراءة migrations وRPCs فقط. لم تُنفذ `EXPLAIN ANALYZE` أو `pg_stat_statements` على Production، لذلك لا ينبغي إضافة فهارس اعتمادًا على التخمين وحده.

| المجال | الملاحظة | الإجراء الآمن المقترح |
|---|---|---|
| `content_metrics` | استعلام `DISTINCT ON` يختار أحدث سجل مع ترتيب متعدد؛ الفهرس الظاهر لا يغطي ترتيب latest-row بالكامل | قياس `EXPLAIN (ANALYZE, BUFFERS)` في staging ثم دراسة فهرس مركب أو snapshot |
| لوحات الموظفين | عدة `count(*)` متكررة على جداول leads وconversations وcontent_items | قياس تكرار الاستدعاء وزمنه، ثم دراسة read model أو cache قصير العمر |
| طوابير العمليات | بعض RPCs تستخدم `select *` مع ترتيب وحدود ثابتة | تحديد الأعمدة المطلوبة ودراسة فهارس `scheduled_for/id` أو `created_at/id` بعد القياس |
| وظائف الوسائط | البحث عن `provider` و`provider_job_id` لا يظهر له فهرس مخصص واضح | التحقق من uniqueness وحجم الجدول ثم إضافة فهرس محدود عند الحاجة |
| سجلات الحجز | حذف retention يتم داخل مسار ingress الساخن مع عدادات لكل طلب | نقل الحذف إلى job دفعي مراقب، مع إبقاء فهارس `attempted_at` وقياس bloat |
| advisory locks | استخدام hash قد يسبب انتظارًا عند التزامن | مراقبة `pg_locks` وlock wait قبل تغيير semantics حفاظًا على الاتساق |

### خطة قياس منخفضة المخاطر

تُنشأ نسخة staging من قاعدة البيانات أو قاعدة مؤقتة، ثم تُجمع عينة من `pg_stat_statements` و`pg_stat_user_indexes` و`pg_locks`. بعد ذلك تُقارن خطط الاستعلامات الأربعة: latest `content_metrics`، طابور العمليات، lookup وظائف الوسائط، ومسار ingress. لا يُطبق أي فهرس على Production إلا إذا ظهر تحسن واضح وكانت كلفته على الكتابة مقبولة.

## 4. الحالة الأمنية الحالية

### ضوابط جيدة تم التحقق منها

مسار الحجز يستخدم Zod للتحقق من المدخلات، ويمرر الطلب إلى `supabaseSecretRpc` بدل كشف مفتاح Supabase للمتصفح. توجد حدود للطول، وUUID للـ idempotency، وhoneypot، وقياس زمن النموذج، وrate limiting. كما أن RPCs الحساسة تستخدم `SECURITY DEFINER` مع `search_path` صريح، وتوجد قيود RBAC وفحوص source-boundary في CI. جلسات الموظفين تستخدم خصائص `HttpOnly` و`Secure` و`SameSite=Lax` بحسب الملف الذي تمت مراجعته. استجابات الحجز تستخدم `Cache-Control: no-store`.

### المخاطر المؤكدة أو المحتملة

| الأولوية | الحالة | الأثر المحتمل | الإجراء المقترح |
|---|---|---|---|
| عالية | `npm audit` وجد 3 عالية و1 متوسطة | استغلال غير مباشر في أدوات البناء أو DoS أثناء parsing | تحديث تدريجي للتبعيات في فرع مستقل، ثم `npm test`, `typecheck`, `lint`, `build` وpreview |
| متوسطة | لا يظهر CSP صريح | تقليل دفاع المتصفح ضد XSS وسوء تحميل الموارد | بدء CSP Report-Only على preview، ثم enforcement بعد مراجعة كل المصادر |
| متوسطة | لا يظهر HSTS صريح | حماية أقل ضد downgrade على أول اتصال | تفعيل HSTS بعد التأكد من HTTPS الكامل والنطاقات الفرعية |
| متوسطة | حماية CSRF الموحدة غير ظاهرة لمسارات Cookie-based | احتمال قبول mutation من سياق متصفح غير مقصود | Origin/Referer allowlist أو CSRF token مع اختبارات regression |
| متوسطة | limiter داخل ذاكرة العملية ويعتمد على مصدر proxy | اختلاف الحماية بين النسخ واحتمال spoofing للرأس | limiter موزع أو مستند إلى خدمة موثوقة، وتثبيت قائمة proxy الموثوق |
| متوسطة | سياسة الاحتفاظ موثقة لكن لا توجد deletion job ظاهرة | بقاء PII أطول من المدة المقصودة | job حذف أو anonymization مراقب بعد اعتماد السياسة التشغيلية |
| منخفضة/تحقق | تاريخ grants متعدد في migrations | اختلاف بين قاعدة قديمة وجديدة | اختبار fresh وupgrade وفحص `routine_privileges` و`has_function_privilege` في قاعدة اختبار |

## 5. ما لم أفعله عمدًا

لم أشغّل `npm audit fix` لأن تحديث lockfile قد يغيّر تبعيات البناء دون اختبار كامل. لم أضف CSP أو HSTS مباشرة لأنهما قد يمنعان موارد صحيحة أو نطاقات لازمة إذا فُعّلا دون معاينة. لم أنفذ `CREATE INDEX` أو `DELETE` أو retention job في Production. لم أختبر endpoints بطريقة هجومية، ولم أرسل حجزًا تجريبيًا جديدًا.

## 6. ترتيب التنفيذ المقترح

1. معالجة تبعيات npm عالية الخطورة في فرع مستقل مع تشغيل الاختبارات وbuild وpreview.
2. إضافة اختبار idempotency والتزامن على قاعدة مؤقتة، لأنه يعالج مباشرة خطر التكرار والعطل السابق.
3. إضافة الاختبارات السلوكية للصلاحيات وRLS وRPC على fresh وupgrade databases.
4. جمع قياسات أداء staging قبل إضافة فهارس أو تعديل RPCs.
5. تشغيل CSP Report-Only ثم مراجعة النتائج قبل enforcement، وإضافة HSTS بعد التحقق من النطاقات.
6. تنفيذ retention deletion أو anonymization بعد اعتماد مدة الاحتفاظ ومجال البيانات رسميًا.
